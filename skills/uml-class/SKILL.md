# uml-class

Диаграмма классов из типизированного JSON: рендерер считает раскладку, рисует инлайн-SVG
и упаковывает всё в один офлайновый HTML-файл.

## Когда использовать

- «Покажи архитектуру кода диаграммой классов» — по папке, файлам или фрагменту проекта.
- «Кто использует `OrderService`?», «Что наследует `PaymentGateway`?»
- «Отобрази все классы и их взаимосвязи, с методами».

Не использовать для схем развёртывания, последовательностей вызовов во времени, ER-диаграмм
баз данных и графиков чисел — это другие инструменты.

## Порядок работы

### C#-проект: сначала экстрактор, не читать файлы руками

```bash
node bin/uml.mjs extract csharp <папка> --out spec.json --stats
node bin/uml.mjs render class spec.json out/classes.html
node bin/uml.mjs check out/classes.html
```

Это дешевле на порядки: разбор идёт локально, агенту не нужно читать исходники. `--stats`
печатает число файлов, классов, связей и «вес» спеки в токенах.

Полезные флаги:

| Флаг | Зачем |
|---|---|
| `--root <dir>` | от какой папки считать относительные пути (подписи зон) |
| `--package-by auto\|folder\|namespace\|none` | `auto` по умолчанию: папки, если namespace в проекте один, иначе namespace |
| `--include <glob>` / `--exclude <glob>` | сузить объём, например `--exclude "**/Editor/**"` |
| `--calls` | добавить зависимости по вызовам внутри методов (`_field.Call()`, `new T()`, `GetComponent<T>()`) |
| `--no-fields` | не рисовать связи от полей и свойств (только базы, интерфейсы и — с `--calls` — вызовы) |
| `--no-deps` | не рисовать зависимости от параметров методов |
| `--title <text>` | заголовок диаграммы |
| `--out <file>` | куда писать спеку (иначе stdout) |
| `--json` | машиночитаемая статистика вместо спеку в stdout |

Экстрактор понимает `class/interface/struct/enum/record`, модификаторы, `partial` (сливает
части), вложенные типы, дженерики, атрибуты, `readonly`/`const` поля, свойства с `get/set/init`,
события, конструкторы, expression-bodied члены, `#if`-блоки, обычные/verbatim/интерполированные
строки. Внешние типы (`MonoBehaviour`, `Vector3`, `Action`) в узлы не превращаются.

После извлечения **проверьте спеку глазами**: экстрактор видит структуру, но не смысл. Часто
стоит убрать служебные связи, добавить подписи и удалить лишние классы.

### Всё остальное: собрать спеку вручную

1. **Прочитать код.** Определить, какие классы входят в запрошенный объём: имена, поля,
   свойства, конструкторы, методы, связи. Связи брать из фактов кода (наследование, реализация
   интерфейса, поля-ссылки, вызовы в методах), а не из догадок.
2. **Собрать `spec.json`** по схеме `schemas/class.schema.json`. Пример — `examples/payments.json`.
3. **Проверить:** `node bin/uml.mjs validate spec.json`.
4. **Отрендерить:** `node bin/uml.mjs render class spec.json out/classes.html`.
5. **Проверить артефакт:** `node bin/uml.mjs check out/classes.html`.
6. **Вернуть пользователю** абсолютные пути к HTML и к `spec.json`, число классов и связей,
   и честно сказать, что визуальную проверку делает он.

Все пути в командах считаются от текущего рабочего каталога. `bin/uml.mjs` — путь внутри
этого скилла; подставьте его полностью, если запускаете из другого каталога.

## Формат `spec.json`

```json
{
  "schemaVersion": 1,
  "title": "Проект: commerce",
  "classes": [
    {
      "id": "order-service",
      "name": "OrderService",
      "stereotype": "class",
      "package": "commerce",
      "fields": ["- repo: OrderRepository"],
      "properties": ["+ Total: Money { get; private set; }"],
      "constructors": ["+ OrderService(repo: OrderRepository)"],
      "methods": ["+ place(order: Order): Receipt"]
    }
  ],
  "relations": [
    { "from": "stripe", "to": "payment-gateway", "kind": "inheritance" },
    { "from": "payment-gateway", "to": "payment-provider", "kind": "realization" },
    { "from": "order-service", "to": "payment-provider", "kind": "dependency", "label": "charge(card, amount)" },
    { "from": "order", "to": "order-line", "kind": "composition", "fromMultiplicity": "1", "toMultiplicity": "1..*" }
  ],
  "packages": [
    { "id": "commerce", "label": "module: commerce", "classes": ["order-service"] }
  ]
}
```

Правила:

- `id` уникален, допустимы латиница, цифры, `_ . : -`.
- `from`/`to` ссылаются на существующие `id`; связь класса с самим собой не поддерживается.
- `kind`: `inheritance`, `realization`, `dependency`, `association`, `composition`, `aggregation`.
- `fromMember` / `toMember` — необязательные строки: подстрока поля, конструктора или метода.
  Когда узел раскрыт, стрелка идёт к этому члену класса, а не к шапке. Без них скилл ищет член,
  в тексте которого встречается имя класса с другой стороны связи.
- Члены класса — свободные строки, рисуются как есть, порядок сохраняется, пустые группы не рисуются.
- `packages` необязателен; класс входит максимум в один пакет.
- Классы, которые лежат **вне** анализируемой папки (интерфейсы, утилиты, чужие типы),
  складывайте в отдельный пакет с `id: "external"` и `label: "External"`. Так на схеме видно,
  что относится к запрошенному коду, а что пришло извне.
- Стрелка наследования и реализации направлена **на родителя**; родитель рисуется выше ребёнка.

## Внешний вид и интерактив

- Тёмная тема по умолчанию (кнопка «Тема» переключает на светлую).
- Каждый класс получает свой цвет по золотому углу: соседние классы гарантированно различаются.
  Заливка полупрозрачная, ползунок «заливка» меняет её от 0 до 80%.
- Раскрытый класс показывает более светлое «тело»: шапка остаётся окрашенной, внутренняя часть — почти прозрачной.
- Члены класса окрашены оттенками цвета класса; в свёрнутом виде они скрыты.
- Каждый член — отдельный контейнер: наведение подсвечивает строку, её стрелку и связанный член
  на другом конце, остальное приглушается.
- Стрелки — градиент от цвета источника к цвету цели. Ромбов и числовых бейджей нет.
- Стрелки выходят и входят только через левый или правый край; при нехватке места линия уходит
  в свободный коридор правее схемы.
- Класс можно перетащить мышью — линии и подписи перестраиваются на лету, холст и рамки пакетов
  расширяются под новое положение.
- Раскрытие узла (стрелка внизу) уточняет стрелки: они привязываются к конкретным членам класса.

## Как выглядит результат

- Класс — прямоугольник со стереотипом и именем. По умолчанию свёрнут: видно только шапку
  и стрелку снизу.
- Нажатие на стрелку разворачивает узел: поля → свойства → конструкторы → методы.
- Наведение на класс подсвечивает все его связи и соседей, остальное приглушается.
- Наведение на линию подсвечивает её и оба конца.
- **Клик по связи закрепляет её**: ребро толще, концы подсвечены, остальное гаснет. Так путь
  не теряется при движении мыши. Повторный клик, кнопка «Снять закрепление» или `Esc` снимают.
- Вверху: поиск по классам, «развернуть все», «свернуть все», тема, сброс вида.
- Файл полностью автономен: CSS и JS внутри, без CDN, без сети.

## Ограничения

- До 300 классов — норма; 300–800 — предупреждение; больше 800 — отказ с кодом 2.
- Нет парсинга исходников: `spec.json` готовит агент, прочитав код.
- Нет экспорта PNG/SVG: результат — HTML.
- Полный UML не поддерживается: нет шаблонов, ограничений `{...}`, диаграмм объектов.

## Что вернуть пользователю

1. Абсолютный путь к HTML и к `spec.json`.
2. Короткую сводку: сколько классов, связей, пакетов.
3. Прямо сказать: «откройте файл, проверьте раскладку и подсветку» — браузерную проверку
   делает человек, а не агент.
